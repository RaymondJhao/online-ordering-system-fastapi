# 0007. 免費方案的部署取捨

**狀態**：已採用

## 背景

這個專案是求職作品集，需要一個隨時可以點開的線上展示。預算為零，
因此全部跑在免費方案上：前端 Vercel、後端與 Redis 在 Render、
資料庫用 Render PostgreSQL。

免費方案有三個會直接影響使用體驗的限制：

| 限制 | 影響 |
|---|---|
| Render Web Service 閒置 15 分鐘後休眠 | 下一位訪客要等 30–60 秒冷啟動 |
| Render PostgreSQL 建立後 30 天到期 | 需要手動重建，且資料全失 |
| Render Key Value（Redis）無持久化 | 重啟即清空，25 MB / 50 連線 |

## 決定一：不做定時保溫，改為誠實的 UI 提示

**考慮過的選項**

用外部 cron（UptimeRobot、cron-job.org）每 10 分鐘打一次 API，讓服務不休眠。

**代價**：Render 免費方案每月 750 instance hours，而一個月有 730 小時。
24 小時保溫等於用掉幾乎全部額度，workspace 裡再也放不下第二個免費服務。
限縮到每天 16 小時可以留下邊際，但仍要維護一個外部服務的排程。

**決定**：不保溫。

理由是這個專案的生命週期本來就有限——它是求職作品集，錄取之後就不需要
維持 24/7 熱機。為了一個註定會被閒置的展示站去長期佔用額度並不划算。

既然接受冷啟動，就把它處理得體面：

1. `App` 掛載時立刻在背景打一次 `/health/live`，讓使用者瀏覽菜單的同時
   後端已經在啟動
2. 等待超過 2 秒才顯示提示橫幅，避免熱機狀態下閃一下反而干擾
3. 明確告知「約需 30–60 秒，此為免費方案的休眠機制，非系統異常」，
   而不是讓畫面空白轉圈
4. axios 的 timeout 設為 90 秒，否則第一個請求會在服務醒來前就失敗

**附帶的架構調整**：把健康檢查拆成 `/health/live`（不碰相依服務）與
`/health/ready`（完整檢查）。`healthCheckPath` 必須指向前者——若健康檢查
在資料庫不通時回 503，Render 會判定實例不健康而反覆重啟，而免費資料庫
每 30 天就有一段重建空窗期，那時最不需要的就是重啟迴圈。

liveness 的語意是「要不要重啟我」，readiness 才是「能不能把流量給我」。
這個區分在 Kubernetes 是常識，但在單機部署常被混為一談。

## 決定二：留在 Render PostgreSQL，接受每 30 天手動重建

**考慮過的選項**

- **Supabase**：無 30 天限制，但閒置 7 天會暫停需手動恢復；
  直連只解析 IPv6，必須走 Supavisor pooler，且 transaction 模式與 asyncpg
  的 prepared statements 衝突
- **Neon**：無 30 天限制，但免費方案每月只有 100 CU-hours，
  且閒置 5 分鐘就 scale to zero（無法關閉）

**決定**：留在 Render PostgreSQL。

主要理由是**不想在求職期間同時導入不熟悉的第三方服務**。Supabase 的
pooler 模式選擇、Neon 的 CU-hours 計費與 scale-to-zero，都需要實際部署過
才會知道踩到什麼。多引入一個變數，就多一處在關鍵時刻壞掉而不知道為什麼的可能。

這是「已知的麻煩」勝過「未知的麻煩」的判斷。30 天重建雖然要手動，
但每一步都清楚可預期。

**代價與緩解**

代價是每 30 天要重建一次，且資料全失。最糟的失敗模式是**靜默的**：
招募方點開連結看到錯誤頁，不會寫信告訴你。

緩解方式是讓重建盡量無腦：

```yaml
preDeployCommand: alembic upgrade head && python -m scripts.seed --if-empty
```

`--if-empty` 讓這行對一般部署毫無作用，只有在資料庫是空的時候才會灌入
展示資料。重建流程因此縮短為「建新 DB → 貼上新的連線字串 → 存檔」，
結構與 demo 資料都會自動回來。

同時 `render.yaml` 刻意**不宣告 `databases:`**：免費資料庫重建後連線字串
會改變，用 `fromDatabase` 綁定會讓 blueprint 與實際資料庫的對應關係斷掉。
改為手動建立、`DATABASE_URL` 設 `sync: false`，行為比較可預期。

**連線字串的正規化**也是為此而做：平台注入的是 `postgresql://`，
還常附帶 `?sslmode=require`——前者讓 async SQLAlchemy 拋
「The asyncio extension requires an async driver」，後者讓 asyncpg 拒絕
未知參數。兩個錯誤訊息都像「連線字串填錯」，重建當下最不需要的就是這種誤導。
在設定層一次處理掉，重建時就真的只是複製貼上。

## 決定三：接受 Redis 無持久化，但誠實記錄

Render 免費的 Key Value 重啟即清空。這對本專案的影響是具體的：
refresh token 的白名單存在 Redis，一旦清空，所有使用者下次換發時都會被
判定為「重用」而撤銷整條 family，等於全站同時登出。

**沒有在免費方案內解決這件事**——真正的解法是付費的持久化 Redis，
或把白名單搬回資料庫（但那會失去 TTL 自動清理的優點）。

決定是接受它，並把限制寫進 README 與 ADR 0003 的更正段落。
文件宣稱了做不到的事，比沒寫更糟。

## 這些決定在什麼情況下會是錯的

如果這個專案要長期營運、或有真實使用者，上述三個決定全部都該重新評估：
冷啟動會直接趕走訪客、每 30 天的資料歸零不可接受、
使用者被隨機登出更是不可能容忍。

它們成立的前提只有一個——**這是一個生命週期以月計算的展示專案**。
把這個前提寫下來，是為了讓日後（或面試時）能清楚說明
「我知道這不是正確的生產架構，我知道正確的做法是什麼，
以及我為什麼在這個情境下選擇了不同的路」。
