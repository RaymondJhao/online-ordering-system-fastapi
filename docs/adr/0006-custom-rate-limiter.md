# 0006. 自行實作 Redis 限流而非使用套件

**狀態**：已採用

## 背景

Flask 版用 `Flask-Limiter` + Redis，對下單（5/min）與結帳（3/min）做頻率限制。
FastAPI 沒有對等的成熟方案。

## 考慮過的選項

**`fastapi-limiter`。** 生態系中最常被推薦的選擇。實際安裝後發現 0.2 版
已改成 `pyrate_limiter` 的薄包裝：`FastAPILimiter.init()` 這個多數文件與教學
都在用的入口已經不存在，改成要自行建構 `pyrate_limiter` 的 `Limiter` 並傳入。
可以用，但等於要同時學兩個套件的 API，而且下一次破壞性變更不知何時會來。

**`slowapi`。** Flask-Limiter 的 Starlette 移植版，API 熟悉，但維護頻率偏低。

**自行實作。** 需求只有「每 N 秒最多 M 次」，約 60 行。

## 決定

自行實作。這個決定的關鍵不是「不想裝套件」，而是：
需求極為單純、演算法是標準做法、可以被完整測試，
而外部套件在這裡帶來的是版本風險而非省下的工作量。

## 實作重點

**滑動視窗日誌（sliding window log）而非固定視窗計數器。**
固定視窗（`INCR` + `EXPIRE`）在視窗交界處會放行兩倍請求——
第 59 秒打滿 5 次、第 61 秒又打滿 5 次，兩秒內實際放行了 10 次。
滑動視窗用 sorted set 記錄每次請求的時間戳，判斷時先移除視窗外的紀錄，
沒有這個破口。

**用 Lua 腳本確保原子性。**
「檢查目前數量」與「寫入本次紀錄」必須是同一個操作，
理由與 ADR 0005 的原子扣庫存完全相同：分成兩次往返時，
多個並行請求會同時通過檢查，實際放行量超過上限。
Redis 的 Lua 腳本在單執行緒中完整執行，天然具備原子性。

**回傳標準標頭。**
`X-RateLimit-Limit`、`X-RateLimit-Remaining`，以及被擋下時的 `Retry-After`
（RFC 9110 對 429 的建議），讓客戶端知道該等多久而不是盲目重試。

## 代價與已知限制

- **以 IP 識別，不是以使用者識別。** 同一個 NAT 或公司網路後的多位使用者
  會共用計數器。改用登入者 id 更精準，但那要求認證依賴先於限流執行，
  會讓兩者的順序變成隱性契約。目前規模下不值得換取那份脆弱性。
- **信任 `X-Forwarded-For` 的第一段。** 這在反向代理之後是必要的
  （否則所有請求看起來都來自代理伺服器），但該標頭可以偽造，
  只有在確定服務位於可信代理之後時才該採信。
- **沒有套件的進階功能。** 例如多層級限制、動態調整、豁免名單。
  需要時再引入套件不遲。

## 如何證明它有效

`tests/test_scheduler_and_limit.py` 涵蓋：超過上限回 429、
`Retry-After` 標頭存在且為正數、未達上限回傳正確的剩餘次數、
不同 scope 的計數器互不影響、關閉設定時不生效。
